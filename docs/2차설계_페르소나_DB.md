# 2차 설계 — MVP 페르소나 3종 & DB 구상

> 근거: [1차생각.md](./1차생각.md) — "Who you are가 아니라 What you're doing".
> MVP는 회원가입·마이데이터 없이 **페르소나 선택**으로 시작한다. 페르소나가 곧 데모 시나리오다.

---

## 1. 페르소나 설계 원칙

페르소나 3명은 그냥 "다양한 사람"이 아니라, **심사위원에게 보여줄 매칭 시나리오 3종**이다.

| | 페르소나 1 | 페르소나 2 | 페르소나 3 |
|---|---|---|---|
| 시연 포인트 | **시험·응시료** 매칭 | **면접·이동** 매칭 | **교육·전환 + 생활비** 매칭 |
| 취준 단계 | 갓 졸업 (초반) | 장기 취준 (중반) | 퇴사 후 전환 (재출발) |
| 지역 | 서울 **중랑구** | **경기** 수원시 | 서울 관악구 |
| 지역 선택 이유 | 중랑구 자격증 응시료 지원(최대 10만 원) 실존 → "구 단위 정책까지 찾아준다" 시연 | 경기도 면접수당 실존 + 서울로 이동 면접 → 광역 이동·교통비 시나리오 | 서울 청년수당·청년월세 등 시·구 정책 조합 |

세 명이 **같은 일정("면접")을 적어도 지역·상태에 따라 다른 혜택**이 붙는 걸 보여주는 게 핵심.

## 2. 프로필 스키마 — "정책 요건에 실제로 등장하는 항목만"

자격 판정 요건을 역산해서 필드를 정한다. 요건 문장에 안 나오는 정보는 수집하지 않는다.

| 그룹 | 필드 | 쓰이는 곳 (실제 요건 예) |
|---|---|---|
| 기본 | 생년월일, 성별 | 나이 요건 (19~34세 등) |
| 기본 | **병역** (군필 여부·복무개월) | 군필자는 나이 상한 연장되는 정책 존재 |
| 거주 | 시도·시군구, **거주 시작일** | "관내 1년 이상 거주" 지자체 요건 |
| 학력 | 상태(재학·휴학·**졸업유예**·졸업), 졸업일, 전공 | 재학생 제외 / "졸업 후 2년 이내" 요건 |
| 취업 | 상태, 미취업 개월수, 목표 직무 | 국취제·수당류 공통 |
| 취업 | **고용보험 이력** (총 가입개월, 최근 이직일) | 실업급여 자격, 국취제 유형 구분 |
| 소득 | 본인 월소득(근로·알바) | "주 30시간 미만 근로" 등 제외 조건 |
| 소득 | **가구 중위소득 구간** (%) | 국취제 60%↓, 청년수당 150%↓ — 현금성 정책 1순위 관문 |
| 소득 | **건강보험 자격** (직장·지역·피부양자) | 건보료 기준 소득 판정 정책 다수 |
| 재산 | **가구 재산 구간** | 국취제 "4억 이하" 등 |
| 가구 | 가구 형태·가구원 수 | 1인가구 요건, 가구소득 산정 |
| 주거 | 주거 형태, **보증금·월세 금액** | 청년월세지원 "보증금·월세 상한" 요건 |
| 수급 | **수급 중인 제도** (금액·종료예정일) | 중복 수급 배제 + 종료 시점 lifecycle 알림 |
| 수급 | **수급 이력** (과거 참여 정책) | 기수령자 제외·재참여 제한 — 없으면 AI가 받은 걸 또 추천함 |
| 스펙 | 보유 자격증·어학 | 훈련과정·일경험 매칭 참고 |

값이 없는 필드는 `null`("모름")로 두고, AI는 추측하는 대신 **"추가 확인 필요 + 확인할 항목"**을 답한다 (Trust 원칙).

## 4. 데이터 모델 (Supabase = PostgreSQL)

```
personas (페르소나 원본, 시드 데이터)
  id            text PK        -- 'minji' | 'junho' | 'seoyeon'
  name          text           -- 김민지
  birth_date    date
  region_sido   text           -- 서울특별시
  region_sigungu text          -- 중랑구
  gender        text
  military      jsonb          -- {군필여부, 복무개월} | null
  residence_since date         -- 거주 시작일
  education     jsonb          -- {상태(재학|휴학|졸업유예|졸업), 전공, 졸업일}
  employment    jsonb          -- {상태, 미취업개월, 목표직무, 본인월소득}
  insurance     jsonb          -- {고용보험총개월, 최근이직일, 건보자격(직장|지역|피부양자)}
  income_bracket text          -- 가구 중위소득 구간: '~60%'|'60~100%'|'100~150%'|'150%~'|null
  asset_bracket text           -- 가구 재산 구간
  household     jsonb          -- {가구형태, 가구원수, 주거형태, 보증금, 월세}
  certificates  text[]         -- 보유 자격증·어학
  receiving     jsonb[]        -- 수급 중 제도 [{이름, 월액, 종료예정일}]
  benefit_history jsonb[]      -- 과거 수급 이력 (중복 배제 판정용)
  intro         text           -- 선택 화면에 보여줄 한 줄 소개

sessions (MVP의 '사용자' = 익명 세션)
  id            uuid PK (default gen_random_uuid())
  persona_id    text FK → personas
  created_at    timestamptz
  -- 로그인 없이: 페르소나 선택 시 세션 생성, id를 브라우저 localStorage에 보관

events (캘린더 일정 — 서비스의 심장)
  id            uuid PK
  session_id    uuid FK → sessions
  date          date
  title         text           -- "SKT 면접" (사용자가 적은 원문)
  event_type    text           -- INTERVIEW|EXAM|EDUCATION|APPLICATION|BENEFIT_END|OTHER (LLM 분류)
  location      text           -- LLM이 추출 ("성남")
  source        text           -- 'user' | 'ai' | 'seed'
  created_at    timestamptz

matches (이벤트 ↔ 정책 연결 = "일정에 붙은 돈")
  id            uuid PK
  event_id      uuid FK → events
  session_id    uuid FK → sessions
  policy_name   text           -- "경기도 청년 면접수당"
  policy_url    text           -- 공식 링크 (Trust 원칙)
  benefit_type  text           -- CASH|VOUCHER|RENTAL|SERVICE
  saving_min_krw integer       -- 절약액 하한
  saving_max_krw integer       -- 절약액 상한 (예: 50,000)
  eligibility   text           -- LIKELY|NEEDS_CHECK|UNLIKELY (모르면 추측 않기)
  ai_reason     text           -- 판단 근거
  evidence_todo text[]         -- ["면접확인서 수령", "영수증 보관"]
  deadline      date           -- 신청 마감
  status        text           -- SUGGESTED|PLANNED|APPLIED|RECEIVED|DISMISSED
  created_at    timestamptz

chat_messages (AI 채팅 기록)
  id            uuid PK
  session_id    uuid FK → sessions
  role          text           -- user|assistant
  content       text
  created_at    timestamptz
```

- **절약 리포트**(주간/월간)는 별도 테이블 없이 `matches`를 기간·status로 집계 (`sum(saving_max_krw)`)
- 페르소나 원본은 코드(`src/data/personas.ts`)가 단일 소스 → 시드 스크립트로 DB에 복사 (수정·리뷰가 git으로 관리됨)
- 정책 원본 DB화(policies 테이블)는 다음 단계 — MVP에서는 LLM 매칭 결과를 matches에 바로 저장

## 5. DB 연동 방법 (Next.js + Supabase)

```
브라우저 ──(fetch)──▶ Next.js API Route (서버) ──(service key)──▶ Supabase
                     · LLM 호출도 여기서              · 키는 Vercel 환경변수
```

1. **Supabase 프로젝트 생성** (supabase.com, 무료·카드 불필요) — 본인 계정으로 가입 → New project → 리전 Seoul
2. 프로젝트에서 두 값 복사: `Project URL`, `service_role key` (서버 전용 비밀키)
3. Next.js에 `@supabase/supabase-js` 설치, `src/lib/supabase.ts`에서 서버 전용 클라이언트 생성
4. **모든 DB 접근은 API Route를 통해서만** (`/api/events`, `/api/matches`, `/api/chat`) — 브라우저에 DB 키가 노출되지 않고, RLS(행 단위 보안) 설정을 MVP 단계에서 고민할 필요 없음
5. 키는 로컬 `.env.local`(gitignore) + Vercel 환경변수 두 곳에 등록
6. 테이블 생성은 Supabase 대시보드 SQL Editor에 위 스키마 붙여넣기 (SQL 파일로 repo에 보관: `supabase/schema.sql`)

**왜 이 구조인가**: LLM 키도 어차피 서버에만 둬야 하므로, "일정 등록 → LLM 분류 → 정책 매칭 → matches 저장"이 전부 API Route 한 곳에서 처리됨. 브라우저는 화면만 담당.

## 6. MVP 사용자 흐름 (페르소나가 끼는 위치)

```
랜딩 → [시작하기]
  → /app/start : 페르소나 3장 카드 중 선택
  → 세션 생성 (sessions insert, localStorage에 세션 id)
  → 시드 일정 자동 등록 (persona의 초기 캘린더)
  → /app : 캘린더 + 채팅 화면
      · 일정 추가 → LLM 분류 → 매칭 생성 → 캘린더에 "돈이 붙음"
      · 상단 절약 리포트: matches 집계
```

## 7. 다음 구현 순서 (제안)

1. `src/data/personas.ts` — 페르소나 3종 데이터 파일
