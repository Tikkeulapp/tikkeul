# RAG 기법 비교와 티끌 적합성 (팀 공유용)

## 1. 기법 진화

| 세대 | 기법 | 핵심 | 약점 |
|---|---|---|---|
| Naive RAG (2023) | chunk → 임베딩 → cosine top-k → LLM | 단순 | 유사≠관련, 조건 필터 불가, 고유명사 약함 |
| Advanced RAG (2024) | 하이브리드(BM25+dense, RRF), 리랭커(cross-encoder), 쿼리 확장(multi-query/HyDE), 메타데이터 사전 필터, Contextual Retrieval | 정밀도·재현율 동시 개선 | 파이프라인 복잡 |
| Agentic RAG (2025~) | Self-RAG, CRAG(결과 품질 평가→웹검색 fallback), Adaptive RAG, 도구 루프(파일시스템·SQL·웹) | 실패 시 자기 복구 | 느림·비용·좋은 모델 필요 |
| GraphRAG (MS 2024) | 엔티티-관계 그래프 + 커뮤니티 요약 | 전역 질문 | 구축 비용, 독립 문서엔 과함 |
| Structured RAG | Text-to-SQL, 메타데이터 필터 | 정형 조건 100% | 비정형 의미 무력 |

## 2. 티끌 v1의 위치

`SQL 조건필터 → LLM 키워드 확장(multi-query 변형) + ilike → LLM 리랭킹`
= Advanced RAG 변형(임베딩 없는 "메타데이터 필터 + 어휘 검색 + LLM 리랭커"). Naive RAG보다 구조적으로 앞섬(조건 필터 선행).

## 3. 적합성 판단

| 기법 | 적합도 | 판단 |
|---|---|---|
| 메타데이터 사전 필터(SQL) | ★★★ 있음 | 지역·나이·마감은 규칙으로 100% 보장 |
| 하이브리드 + RRF | ★★★ v2 | 고유명사(키워드)+패러프레이즈(벡터). pgvector + BGE-m3 — 팀원 담당 |
| 리랭커(bge-reranker-v2-m3) | ★★☆ v2 추가 권장 | 후보 50→10 정밀 압축, LLM 토큰↓·비결정성↓ |
| 쿼리 확장 | ★★★ 있음 | LLM 키워드 확장(범용어 제거 적용) |
| CRAG식 fallback | ★★☆ | 후보 빈약 시 웹검색 → **격리 큐** → 검증 후 편입 |
| Agentic 루프 | ★☆☆ | 채팅에만(재검색 1~2회). 실시간 매칭엔 부적합 |
| GraphRAG | ☆ | 정책은 독립 문서. 중복수급 배제 관계만 룰로 처리 |
| Long-context 무검색 | ★★☆ 옵션 | 지역 필터 후 후보 수십 건이면 검색 생략하고 LLM에 통째 투입 가능 (코퍼스가 작아 가능한 지름길) |
| 파일시스템 RAG | ☆ 조회 기법 | 수집·저장 문제와 무관. 조회 시 느리고 비쌈 — 채택 안 함 |

**결론**: 이 도메인의 난제는 "찾기"가 아니라 **"자격 판정"**. 우선순위 = ① eligibility_json으로 조건 필터 정밀화 → ② 리랭커/하이브리드로 후보 품질 → ③ CRAG fallback으로 커버리지.

## 4. 수집 계층 설계 (웹검색·크롤)

| 층 | 소스 | 주기 | 역할 |
|---|---|---|---|
| A 국가 API | 온통청년·gov24 | 일 1~2회 증분(해시 비교) | 공식 본체 |
| B 지자체 포털 크롤 | 17개 시도 청년포털 + 주요 시군구 게시판 | 일 1~2회 | **갱신용 본체** (대전 AI 거점 실사례 커버) |
| C 웹검색 | 후보 빈약 시 트리거 (CRAG) | 요청 시 | **발견용**. 결과는 미검증 |

- 1시간 주기는 과함 — 정책 신규 공고는 일 수십 건. 쿼터·차단 리스크만 증가
- **자동 직접 저장 금지**: 발견물 → `policy_discovery_queue` → 중복 판정(제목 유사도+기관) → 검증 → `policies` 승격 (verification_status=curated)
- 원문 보존은 `policy_sources.raw`(jsonb/text) — "파일 보존" 역할. 파일 RAG 불필요

## 5. "프로필 상태 변화 이벤트" 설계 (이사·졸업·퇴사·취업)

```
일정 등록 → AI가 상태변화 유형 감지 (MOVE/GRADUATE/RESIGN/EMPLOYED)
  → 확인 카드 ("9/25부터 거주지를 대전으로 바꿀까요?")
  → 승인: profile_changes(field, old, new, effective_from, source_event_id)
  → 델타 리포트: 새로 열리는 혜택 N건 / 사라지는 혜택 M건 / 전환 전 신청 유리한 것
  → effective_from 이후 모든 추천·매칭이 새 상태 기준
```
= 1차생각.md의 lifecycle 관리. 일정 매칭(직접 혜택)과는 별도 층.
